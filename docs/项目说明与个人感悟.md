# 识废：同图双方案垃圾识别项目说明

## 问题与实现

本项目比较本地视觉和远端多模态 API 对同一图片的垃圾四分类判断。输入 JPG/PNG/WebP，经解码、EXIF 方向校正和 RGB 统一后，分别交给两条独立链路。按北京生活垃圾口径，结合物品用途、污染和是否已决定丢弃判断；看不清时保留未知。

网页采用 Streamlit，当前默认本地方案为 SAM2.1 tiny 分割 + CLIP ViT-B/32 区域文本匹配，配合上下文、分类描述和碎片过滤。输出原图、区域框、物品清单、四分类、不确定项、耗时以及 JSON/CSV/标注图。SAM 掩膜质量、CLIP 相似度都不是分类正确概率。整图回退结果明确不提供定位框，不能用于精确计数。

远端当前配置为第三方 NexaVLinks 提供的 `gpt-6-astra`，通过兼容 Chat Completions 的图片接口请求结构化结果。名称来自该平台，不能据此独立证明上游模型身份，也不能称作 OpenAI 官方直连。官方 OpenAI Responses 和历史百炼适配保留，但不是当前已验证的服务路径。API 独立接收图片和规则，不接收本地模型预测；严格校验 JSON，不虚构框或置信度。真实调用、网络失败及历史结果分别记录。

## 优化与评估

数据来自公开来源，保存许可、来源、图像哈希和分组；不同实验按各自冻结清单划分。参考标签来自元数据和辅助视觉复核，未经独立真人全面标注，小样本和预训练数据重叠均限制结论。

v0.5 的本地输入与描述改进在当时冻结的同组40图上，将类别集合完全一致从26/40提高到33/40，已成为当前默认配置。之后的分类层监督训练在当时新25图上从20/25降至18/25，候选未采用。

v0.7 实际使用707张图、2221个物品框，训练YOLOv8n定位器37轮，最佳epoch25；检测框提示真实SAM掩膜，再接原CLIP分类。检测测试124图上的二值物品定位mAP50为0.4497、mAP50–95为0.2671；这不是垃圾四分类准确率。模型在户外两类图片上改善，但验证集没有改善且部分原正确图片退化，未替换默认方案。

v0.8 在17张已使用的开发图上选择保守补漏规则，随后重放历史同图记录：Commons25图原默认20/25、定位候选22/25、补漏23/25；TACO29图分别14/29、21/29、21/29。这里衡量每张图的四分类集合是否完全一致，不衡量物品名称、框、数量或理由完全正确。两组均已使用过，不能称作新独立测试。另对4张预先选定的历史案例做了无旧分割缓存的真实GPU重跑，恢复2个漏检案例，仍存在混合类别漏检；这些案例不能作为总体正确率。

多模态历史计划40图，尝试38图、有效响应33图、通信失败5图、未请求2图。同38图本地32/38（84.2%）、API28/38（73.7%）；仅看同33张有效响应，两者均28/33（84.8%）。因此可见差距包含通信可靠性，不能直接断言大模型视觉能力普遍更弱。5张语义分歧另有参考范围或规则歧义，未改标签美化成绩。该组与上述25/29图不同，不能跨组直接比较。

详见[模型对比与收尾说明](模型对比与收尾说明.md)及其原始证据链接。v0.8 新增付费请求为0，没有训练远端大模型权重。补漏仍未通过全部回归条件，且没有新的独立留出测试，所以保留实验候选，网页继续原默认模型。本次有界对比已结束，进入个人操作和材料补充阶段。

## 适用场景与局限

本地方案适合不逐次联网、需要区域展示的场景，但小目标、遮挡、堆积和物体部件容易误判。远端方案可解释语义与分类理由，但还受网络、预算、平台和结构输出可靠性影响。两者一致也不代表正确，不能替代正式投放规则。

软件检查覆盖接口、导出、预算和真实GPU页面逻辑；它们不等于识别质量达标，更不等于实际录屏。用户需补充个人经历、理解代码、录制真实操作并按考核要求提交。旧版本报告保留历史意义，最新结论以当前对比说明为准。

## 个人感悟

做这个垃圾识别与分类项目之前，我对模型效果的理解比较简单：只要接入视觉模型或者能力较强的大模型，应该就能得到比较准确的结果。实际使用后，我发现“程序能够运行”和“识别结果可靠”之间还有很大的距离。一个完整项目不仅需要模型，还需要处理图片输入、分类规则、接口连接、结果展示和测试评价等问题。

让我印象比较深的是测试空塑料瓶时，本地模型把瓶盖区域识别成了 LED 灯泡候选，分类显示为无法确定。图片里明明是一个瓶子，模型却可能把它拆成多个区域，再分别判断。这让我开始理解，分割出一个区域并不代表理解了这个物体；页面上出现框和名称，也不能证明结果正确。我也因此更关注模型有没有漏检、误检，以及遇到不确定情况时是否如实提示。

多模态接口的接入同样让我感受到，模型之外的工程问题会直接影响使用体验。我在账号登录、本地配置和接口使用过程中遇到了不少不熟悉的操作，也经历过页面无法访问、接口未启用和请求失败。后来看到对比结果，我才意识到，模型判断错误和网络请求失败是不同的问题：前者关系到识别能力，后者关系到服务可靠性，但对使用者来说，两者都会导致这次任务没有完成。

优化过程也改变了我的认识。我原本以为，继续训练或者换更强的模型，正确率就应该不断上升。实际实验中，有的方案提高了总体成绩，却把原本正确的图片识别错了；有的训练甚至没有带来改善。因此，评价优化不能只看一个百分比，还要看测试图片是否相同、哪些类别变好了、哪些场景退化了，以及测试数据是否已经参与过调整。保留失败实验、不急着替换默认模型，也是项目中需要作出的判断。

目前，我认为这个项目的价值不仅在于识别垃圾，更在于让我经历了从“看到一个结果”到“追问结果是否可信”的过程。如果继续改进，我更愿意先收集和复核一些真实生活中的困难图片，例如混合垃圾、遮挡物品和污染包装，再分析具体错误，而不是只追求更换模型或提高表面分数。

## 代码阅读

下面按图片输入、本地识别、接口处理和结果评价四个环节介绍代码，可结合源码与网页结果阅读。

### 1. 一张图片怎样进入两条识别链路

先看 [app.py](../app.py) 的“开始识别”按钮，再追到 [images.py](../garbage_vision/images.py) 的 `decode_image`。图片会检查真实格式与尺寸、校正拍摄方向、把透明背景合成白底，并统一为 RGB。`image_id` 根据统一后的 PNG 计算，`source_sha256` 根据原始文件计算。页面把同一个 `source` 分别交给 `infer_local` 和 `infer_api`，两条链路不交换预测。

### 2. 本地模型为什么会显示“待确认区域”

阅读 [local.py](../garbage_vision/local.py) 中的 `LocalEngine`、`classify_region` 和 `prune_uncertain_parts`。SAM 提供区域，CLIP 比较图像区域与文本描述；类别判断还需要检查相似度及它与其他类别的分数差。背景候选可能被跳过，证据不足的区域可能被过滤或保留为未知。碎片过滤依据真实掩膜包含关系，不是简单删除所有小框。

### 3. 大模型返回文本后，程序还要做什么

阅读 [api.py](../garbage_vision/api.py) 的 `build_payload`、`infer_api`、`parse_response`，以及 [app.py](../app.py) 中运行结果与历史结果的两个入口。新请求发送图片和规则，返回内容必须经过 JSON 结构与字段校验；网络失败和不符合要求的响应不能当作成功。历史结果按钮读取此前保存的记录，不发起新的识图请求。

### 4. 报告里的“正确率”怎样计算

阅读 [evaluation.py](../garbage_vision/evaluation.py) 的 `set_scores` 和 `score_records`。当前共同比较的是每张图出现的四分类集合；代码核对图片哈希、检查记录是否齐全，并把运行失败计入评价。集合一致不等于物品名称、数量和位置都正确。

手算例子：参考是“可回收物＋其他垃圾”，预测只有“可回收物”，则 TP=1、FP=0、FN=1，Precision=1、Recall=0.5、F1约为0.667，集合完全匹配为假。即使参考集合为空，请求失败也不能算正确。
