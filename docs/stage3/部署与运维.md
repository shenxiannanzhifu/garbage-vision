# 三阶段启动与部署

更新：2026-10-22。Windows服务与本机Linux CPU应用容器均已完成两张开发图真实HTTP验证，容器网页历史/刷新/JSON下载通过。当前访问 `http://127.0.0.1:8080` 即可，不需要再构建。远端Linux服务器尚未部署。

## 本机组件与目录

本机采用 Windows → WSL2 Linux 内核 → Docker Desktop → Linux 应用容器。无需另外安装 Ubuntu 或第二套 Docker Engine。WSL2 内核可用不等于项目已部署，项目以真实容器任务结果为准。

源码和独立 Windows 环境在 `D:/灵境竞赛组/stage3/garbage-vision`；Docker 程序在 `stage3/runtime/docker-app`，实际镜像、容器和构建缓存磁盘在 `stage3/runtime/docker-data`。Windows 系统组件仍有少量 C 盘占用。

## Windows 开发入口（已实际启动）

在三阶段项目目录打开两个普通 PowerShell 窗口，分别运行：

```powershell
.venv\Scripts\python.exe scripts/run_stage3.py api
```


打开 `http://127.0.0.1:8503`。也可双击项目内 `启动三阶段.cmd`。此入口使用三阶段解释器；不要用 Anaconda 的默认 Python。缓存和临时目录仅在当前进程指向 D 盘项目 `.local`，不改系统 HOME。

首次入口生成被 Git 忽略的 `.env.stage3`，包含随机访问凭据。`.env` 保存已有模型供应商配置；两个文件均不可提交、截图或发到聊天。示例 `.env.stage3.example` 不含真实凭据。本阶段收费上限为 0。

## 本机 Linux 应用容器（已运行）

保持 Docker Desktop 与现有代理软件开启。在普通 PowerShell 运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\灵境竞赛组\stage3\garbage-vision\scripts\deploy_local.ps1'
```

脚本依次校验 Compose、构建 CPU 镜像、启动 API/Web/nginx、检查 Linux 依赖、通过 nginx 向后端提交两张开发图并校验真实推理与导出。只有全部完成才显示通过。证据在 `evidence/stage3/linux-container`。本次脚本的镜像构建、依赖检查与服务启动通过，最后的import探针发生PowerShell引号截断，故原 `deploy-summary.json` 仍保留失败。探针已修复；后续助手直接通过HTTP完成真实模型及浏览器验证，记录为 `acceptance.json`（complete=true）、`summary.json` 和逐任务JSON/标注图，未将原脚本记录改写成成功。

两张CPU任务分别约145.076秒（含初次加载）与120.100秒。输入SHA256、服务器规范PNG的SHA256、客户端与服务器解码像素、任务与模型标识均核对一致。跨平台PNG压缩字节不同，验证不要求Windows重编码的PNG与Linux字节一致。浏览器刷新与JSON下载后任务总数仍为2，没有重新执行模型或调用收费API。

构建与容器数据通过 Docker 的 D 盘虚拟磁盘承载；权重只读挂载 `weights`，SQLite 与任务文件挂载 `.local/container-data`。CPU 为当前默认路线，性能需实测。`compose.gpu.yaml` 是待验证的 GPU 扩展，不因基础 CUDA 容器能看到设备就视为完整模型通过。

### 镜像令牌网络故障

当前遇到 `auth.docker.io` 解析到异常 IPv6 后超时。已有本机 HTTP 代理为 `127.0.0.1:7897`，经代理访问令牌服务曾返回 HTTP 200。

Docker 设置 Resources → Proxies 中已保存 HTTP/HTTPS 手动代理，Containers proxy 沿用 host proxy。Windows 上的 buildx 客户端可能独立获取令牌，因此部署脚本还读取当前用户已有 Windows 代理，为本脚本设置 `HTTP_PROXY`/`HTTPS_PROXY`，退出时恢复；不改系统全局代理。脚本丢弃令牌响应，仅显示 HTTP 状态。只保存界面代理后的首次重跑仍超时，客户端代理补丁后基础镜像下载已通过。

客户端代理补丁后，令牌服务200、Python基础镜像下载通过。随后 apt 的 HTTP 软件源出现502/解析失败；Dockerfile 改为 Debian HTTPS并保留签名校验，脚本读取引擎公布的内部 HTTP 代理，作为预定义 build-arg 传给 apt/pip，不把代理写入镜像 ENV。内部代理地址兼容省略协议的格式。修复后apt系统依赖安装通过。

Python依赖安装曾在OpenCV的67MB wheel下载中途超时。修复将安装拆成独立层，pip固定25.3以支持下载恢复，读超时120秒、连接及恢复重试8次，使用BuildKit pip缓存复用完整下载，并在末尾执行pip check。缓存仍位于Docker的D盘数据盘，不打入最终镜像；TLS和固定CLIP源码哈希校验保持启用。修复后的完整镜像构建、依赖一致性和两张真实容器模型推理已通过。

无需为此重装 Docker、关 TLS 校验、修改全局 DNS，或开放未认证的 Docker TCP 接口。助手访问命名管道受限，构建由用户正常终端执行，助手读取 D 盘证据排错。

## 运行、数据与备份

容器运行成功后打开 `http://127.0.0.1:8080`。`/api/` 转发给 FastAPI，其余请求与 WebSocket 转发给 Streamlit。API 不另向宿主机开放端口。

在项目目录使用 Docker CLI（默认 PATH 未配置时先打开 `stage3/进入三阶段环境.cmd`）：

```powershell
docker compose ps
docker compose stop
docker compose up -d --wait
```

停止容器不会删除绑定目录中的 SQLite 与图片。备份应先停止 API，完整复制 `.local/container-data` 和需要安全保存的本地配置；SQLite 正在写入时只复制一个数据库文件不能保证一致。恢复到新目录前保留原备份，不覆盖正在运行的数据。

2026-10-22 已在本机 Docker 完成维护演练：两项原有记录、完整结果和图片哈希在容器重建前后相同；停服备份逐文件 SHA256 核对通过；备份副本在独立 Linux 容器恢复通过，未触发模型调用。证据为 `evidence/stage3/linux-container/persistence.json`、`restore-result.json` 和 `maintenance-20261022-134703-193.json`。原 `deploy-summary.json` 的早期失败记录继续保留。

以后更新本机程序并验证数据保留时，在没有执行中任务的情况下运行以下维护模式。它不会重复两张图片识别，运行期间不要新建任务：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\灵境竞赛组\stage3\garbage-vision\scripts\deploy_local.ps1' -Maintenance
```

此模式保存旧镜像标签、构建新镜像、停止 API 备份数据、恢复并重建服务，然后比较历史和验证恢复副本。数据在 `.local/maintenance/<运行时间>/backup`；`restore-copy` 是可写的演练副本。配置密钥仍留在原有被忽略文件中，不写入公开证据。随后已完成独立版本切换演练，见下文。

本次旧镜像保留为 `garbage-vision-stage3:before-20261022-134703-193`。若需要回滚，先停止新任务并备份当前数据，核对旧版是否支持当前数据库版本，再为 Compose 的 api/web 同时指定该旧镜像并重建；不要仅切换其中一个服务，也不要自动用旧数据库覆盖新任务。遇到结构变化时先在副本上执行迁移与校验。

数据库首次创建后设 `PRAGMA user_version=1`。未标版本但列名集合一致的最早三阶段数据库可原地接纳，完整历史保留已通过测试；未知版本或列集合不一致会拒绝启动。当前检查不替代完整数据库迁移框架；未来结构升级必须新增显式迁移程序，在备份副本上验证后再部署，不能靠删除数据库解决。

原图、结果、导出可能包含使用者上传内容，不进入公开 Git。任务删除不可撤销；防重编号和已预留调用次数仍保留。重启后的中断任务不自动重新推理，明确新建任务才执行。

远端尚未部署，也尚未采购。已依据本机CPU实测与官方当前价格准备[服务器建议](服务器建议.md)，由用户确认预算和账号访问。初期复用单机 Compose、单 worker 与持久化目录；宿主数据目录需让容器用户 UID 10001 可写，按选定服务器实际配置验证，不将 Windows D 盘绝对路径写入容器。

## 已完成的版本回滚演练

`scripts/verify_rollback.ps1` 只使用已有镜像和停服备份，在独立Compose项目/8081端口执行新版本→旧版本→新版本。api/web实际镜像ID分别核对通过，每个阶段都比较完整历史结果和图片哈希，最后关闭测试容器及网络。没有发送推理请求，也没有改变8080的在线服务。2026-10-22已实际通过，证据为 `evidence/stage3/linux-container/rollback-20261022-140037-330.json`。这是本机Linux容器演练；远端仍需按实际部署版本复核。

若以后需要再次演练，在普通PowerShell运行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'D:\灵境竞赛组\stage3\garbage-vision\scripts\verify_rollback.ps1'
```

脚本要求已经完成维护模式、8081空闲及Compose 2.24.4以上（本机5.6.0）。失败记录会保留；备份副本位于 `.local/rollback`，不会自动清空。重复执行只用于版本变化后的必要验证。
