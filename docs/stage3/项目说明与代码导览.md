# 三阶段项目说明与代码导览

本阶段将已经通过二阶段的同图双方案识别程序改造成服务。默认模型仍为 SAM2.1 tiny 与 CLIP ViT-B/32，外部模型接口仍可配置；本阶段没有重新训练，也没有把原有错分和漏检写成已经解决。

## 一次请求如何完成

1. 浏览器打开 Streamlit 页面 `stage3_app.py`，选择图片或开发样例。页面校验图片，显示当前费用选项；点击创建时，生成一个提交编号。
2. `garbage_vision/service_client.py` 通过 HTTP 把图片和提交编号传给 FastAPI。页面不直接加载模型，不会在刷新时重新识别。
3. `garbage_vision/service.py` 校验访问凭据、大小、格式、参数和调用授权。同一编号和同图同参数返回原任务；图片文件使用系统生成的 UUID 目录保存，上传文件名不能指定服务器路径。
4. SQLAlchemy 把任务状态写入 SQLite 后返回任务 ID。单线程后台执行本地模型，若本次获得外部调用授权，再独立对同图请求多模态服务。两侧各自保存结果，一侧失败仍可读另一侧。
5. 网页按任务 ID 查询状态。任务结束后停止定时查询；历史、标注图、JSON 和 CSV 均读取已保存记录。

## 目录与职责

| 文件 | 作用 |
|---|---|
| `stage3_app.py` | 上传、状态、双侧展示、历史、下载和删除入口 |
| `garbage_vision/service.py` | 接口、任务状态、SQLAlchemy 表、授权次数与后台执行 |
| `garbage_vision/service_client.py` | 页面调用后端，创建请求不自动重发 |
| `garbage_vision/local.py` / `api.py` | 沿用二阶段模型封装，服务调用现有能力 |
| `Dockerfile` | Linux 依赖和程序打包，默认 CPU；使用非 root 用户 |
| `compose.yaml` | 启动 api、web、nginx，配置内部网络与持久化挂载 |
| `deploy/nginx.conf` | 统一入口，转发页面、WebSocket 和 `/api/` 请求 |
| `scripts/deploy_local.ps1` | Windows 本机的构建和真实验证；维护模式验证历史和备份 |
| `tests/test_stage3_service.py` | 使用模型替身验证状态、防重、费用及数据库边界 |

镜像是打包好的程序和依赖；容器是镜像运行起来的实例。容器可删除重建，因此数据库、任务图片和权重通过挂载放在容器外。Compose 用一份配置管理三个服务；nginx 把浏览器访问集中到一个端口。

## 数据与异常

任务表记录任务 ID、原图与规范图片哈希、配置指纹、时间、两侧状态和结构化结果。授权表记录本次授权编号、上限和已预留次数，不保存 API 密钥。凭据通过被忽略的环境文件注入。

重启时，遗留的 queued/running 任务改为 interrupted；如果外部请求可能已经发出，则标 unknown，避免误以为失败就再次付费。此处使用单实例进程内执行队列；任务状态落库不等于执行上下文可靠持久化，也不承诺恰好一次请求。

SQLite 的事务保证数据库内的一组改动一起提交，但删除图片和数据库提交不是跨介质原子事务。这是当前局限。部署数据需备份，不能通过删除数据目录修复报错。

## 访问控制与学习范围

当前网页仅绑定本机，API 采用共享 Bearer 令牌。远端已通过 SSH 隧道访问；共享令牌不是多用户账号体系。JWT 是携带签名声明的令牌机制，当前不实现 JWT 登录；如果以后开放多人公网访问，需要独立账号、过期和权限校验。Redis/Celery 可承载独立消息队列，本阶段在单人演示范围内没有引入，不能声称已经采用。

## 已有真实结果

Windows CUDA 与本机 Linux CPU 均已通过两张开发图的 HTTP 识别链路；Linux API、网页与 nginx 运行，容器重建和副本恢复也已验证。细节见[阶段现状](README.md)及[验收与演示](验收与演示.md)。阿里云香港A10已真实部署，两张同图双方案均成功，逐任务JSON、页面截图和费用证据位于`evidence/stage3/remote-linux`。两次实际费用合计0.0617103 NEX。本轮结果是云端新执行，后续历史查看则明确作为回放。用户要求的手动调用模式已上线，默认不勾选且不自动重试。
