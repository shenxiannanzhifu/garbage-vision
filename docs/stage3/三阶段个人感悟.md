# 三阶段个人感悟：把识别程序做成可以运行和维护的服务

## 一、这次项目完成了什么

二阶段完成的是垃圾识别对比：同一张图片分别交给 SAM2.1 tiny＋CLIP ViT-B/32 和外部多模态接口处理，再展示两种方案的结果。第三阶段继续使用这些模型和分类规则，没有重新训练，也没有把部署成功写成识别准确率提高。

这次新增的重点是让程序成为一个可以操作、记录和维护的 Web 应用。网页负责上传图片和展示结果，后端负责校验输入、创建任务和调用模型，数据库负责保存任务与结果。程序还需要在真正的 Linux 服务器上通过 Docker 运行，并且能够查看历史、导出结果、停止启动、备份恢复和切换版本。

最终使用阿里云香港的 Ubuntu 24.04.4 服务器，配置 A10 GPU。网页、FastAPI 后端与 nginx 三个服务通过 Docker Compose 组织。服务器实际完成了两张开发图片的同图双方案调用，后来更新手动调用模式，又通过网页创建了一项只运行本地模型的真实任务。最终保存并备份了四条历史。

这让我看到，模型能够运行只是应用的一部分。图片从哪里来、任务有没有重复执行、失败后能留下什么、重新启动后数据还在不在，这些问题也决定了项目能否真正使用。

## 二、把一次识别过程串起来

我可以用“点单、制作、保存、取结果”来理解这条流程：

1. 在 Streamlit 网页选择图片和本次运行选项，点击“创建识别任务”。
2. 网页通过 HTTP 把图片提交给 FastAPI，附带一个用于防止重复提交的编号。
3. 后端检查图片、参数、访问凭据和收费选项，保存图片与任务记录，返回任务 ID。
4. 后台按顺序执行模型。本地方案和外部方案处理同一张图片，分别保存状态与结果；外部方案不会把本地方案的预测当成答案输入。
5. 网页根据任务 ID 定期查询状态，再展示已经保存的结果。查看历史、刷新状态和下载结果不会重新识别。

这里的“本地模型”表示由项目自己加载权重执行的模型。部署到云端以后，它运行在云服务器的容器中，并不是仍在我的笔记本上计算。

主要代码可以这样对应：`stage3_app.py` 是页面，`garbage_vision/service_client.py` 发送页面请求，`garbage_vision/service.py` 管理接口、任务和数据库，`garbage_vision/local.py` 与 `garbage_vision/api.py` 复用二阶段的两套推理能力。

## 三、Python Web：页面、接口与数据库

### 1. FastAPI、Flask 与接口

**通俗解释：接口像一个有固定收件规则的窗口，别人按约定递交图片，它按约定返回任务编号或结果。**

FastAPI 和 Flask 都可以用 Python 编写 Web 后端，是两种可选框架。本项目实际使用 FastAPI，没有再实现一套 Flask 服务。FastAPI 负责文件上传、参数处理、访问检查以及调用项目功能；Uvicorn 则是实际接收网络请求、运行这个应用的服务程序。

项目的 `POST /v1/tasks` 接口创建识别任务，`GET /v1/tasks/{id}` 查询状态和结果，`DELETE /v1/tasks/{id}` 删除已结束的任务。POST、GET、DELETE 可以分别理解为提交、读取和删除。结果主要用 JSON 返回，即通过字段名和字段值组织的数据，便于页面读取和下载。

创建任务返回 HTTP 202，表示任务已被接收，不表示模型已经完成。格式或参数错误会明确报错，等待任务达到上限会返回 429。这样页面能够说明发生了什么，用户也不用只看着一个没有解释的等待画面。

文件上传还需要检查内容。项目限制图片字节数与像素数，并沿用方向校正、颜色转换和解码逻辑；存储目录由系统生成的 UUID 决定，不直接使用上传文件名作为路径。这些工作保护的是输入与文件管理的正确性，不是提高模型识别率。

### 2. Streamlit 与 Gradio

**通俗解释：它们让 Python 程序有一个可以上传、点击和看结果的操作面板。**

Streamlit 和 Gradio 都适合制作模型演示界面。本项目沿用已有的 Streamlit，没有额外改写 Gradio 页面。界面保留中文操作、同图双侧结果、耗时、未知提示、历史和下载功能。

三阶段的关键变化是页面通过 `service_client.py` 请求后端，主识别流程不在网页进程中直接加载模型。页面更像操作台，后端负责处理工作。创建后，页面使用任务 ID 查询；任务完成后停止定时查询。

Streamlit 的交互可能导致页面代码重新运行，所以“页面重新运行”和“重新提交识别”必须分开。项目把模型调用放在明确的创建动作之后，避免刷新或下载意外变成新的收费请求。

### 3. SQLAlchemy、SQLite 与增删改查

**通俗解释：SQLite 像项目的记事本，SQLAlchemy 帮助 Python 按统一规则读写这本记事本。**

SQLite 是数据库，数据保存在文件中，不需要再运行一个独立数据库服务器。SQLAlchemy 是 Python 操作数据库的工具；其中 ORM 可以把 Python 类与数据库表对应起来，让程序通过对象和查询操作记录。SQLAlchemy 和 SQLite 不是同一种东西。

本项目在 `service.py` 中定义任务表 `Task` 和调用授权表 `Budget`。任务表保存任务 ID、图片标识、时间、选项、两侧状态及结果；授权表保存授权编号、次数限制和已预留次数，不保存服务商密钥。

“增删改查”对应的实际操作是：创建任务时新增记录，执行中修改状态，历史页面查询记录，用户确认后删除已结束任务的图片和结果。删除仍会保留最小的防重复记录及收费预留信息，防止同一个旧提交编号又触发一次识别。

SQLite 文件位于持久化数据目录中的 `tasks.sqlite3`。当前是单实例、小规模演示，使用 SQLite 比再增加一个数据库服务简单；这不等于已经验证了大量用户同时写入的能力。

### 4. 事务、结构版本与持久化

**通俗解释：事务是在数据库里把一组相关修改作为一件事提交；持久化则是让数据在程序退出后仍然留下来。**

任务创建和状态更新需要明确什么时候提交数据库。项目使用 SQLAlchemy 的会话与事务管理这些修改，避免把未完成的数据库修改当成已经保存。

数据库结构也有版本。当前使用 `user_version=1`，启动时检查已有表的列集合和版本；不兼容时拒绝启动，不通过删除旧库来“修好”程序。这是基本兼容性保护，还不是完整的数据库迁移系统。

数据库中的事务不能自动把磁盘文件操作也变成同一个原子操作。例如删除图片和提交数据库仍可能在中途失败，因此备份、错误处理和边界说明同样重要。

## 四、Linux：系统、远程登录与排错

### 1. Windows、WSL2、Linux 服务器与容器

**通俗解释：Windows 是我的工作电脑系统，WSL2 为本机提供 Linux 运行基础，远端服务器是另一台实际运行项目的电脑。**

本机采用 Windows、WSL2 和 Docker Desktop 的组合，Docker Desktop 管理运行 Linux 容器所需的环境，因此没有为了这个项目再安装一套普通 Ubuntu 发行版和另一套 Docker 引擎。云端服务器则单独运行 Ubuntu Linux。

这几个环境不能混为一谈：Windows 中 PyTorch 能使用显卡，不代表容器已经能使用；本机容器测试成功，也不代表远端服务器部署完成。项目先验证本机，再验证云端，并分别保存证据。

### 2. 文件、目录、权限、进程与日志

**通俗解释：目录决定东西放在哪里，权限决定谁能动它，进程表示谁正在运行，日志记录它做到了哪一步。**

Windows 的 `D:\...` 路径不能直接当成容器里的 Linux 路径。容器中程序位于 `/app`，数据位于 `/data`，这些路径通过挂载与宿主机目录关联。Linux 还区分大小写，脚本的换行方式和命令参数引用也可能影响运行。

权限方面，应用镜像使用普通用户 `appuser`，UID 为 10001；数据目录要允许这个用户写入，权重目录则按只读方式挂载。管理员能访问某个目录，不代表普通应用进程也能访问，所以遇到“拒绝访问”时要先确定是哪一个进程、哪一层权限出了问题。

本项目的排错需要区分页面、API、容器和服务器。`docker compose ps` 用于查看服务状态，`docker compose logs` 用于定位日志。Linux 的 `pwd`、`ls`、`cd` 用于确认和切换位置，`ps` 用于查看进程；这些是需要逐步熟悉的基础命令，并不表示我已经可以脱离说明熟练完成全部运维。

### 3. SSH、密钥与隧道

**通俗解释：SSH 是通往远端电脑的加密通道，隧道还能把远端应用的入口接到自己电脑的一个端口上。**

本项目使用 SSH 密钥登录服务器。私钥由本人安全保管，不进入 Git 仓库、交付源码包和演示画面；连接时还需要核对服务器身份，不能只因为知道一个地址就跳过验证。

服务器的 nginx 入口绑定在服务器自己的回环地址，通过 SSH 映射到我的电脑 `127.0.0.1:18080`。浏览器访问这个地址时，真正处理识别的是云服务器。原来的 `127.0.0.1:8080` 则是本机容器入口。

`127.0.0.1` 的意思是“当前这台电脑自己”，因此不能把这个链接直接发给另一台电脑上的评审，并认为对方也能看到我的服务器页面。评审可以先看视频与代码；需要在线操作时，再安排受控访问。

### 4. 依赖、虚拟环境与环境变量

**通俗解释：依赖是程序需要的工具，虚拟环境把不同项目的工具分开，环境变量告诉程序本次怎样运行。**

三阶段使用独立 Python 环境，避免修改二阶段已验证环境，也不混用 Anaconda 默认解释器。Linux 容器按依赖文件重新安装兼容的软件包，不能直接复制 Windows 的 `.venv` 进去。

设备、数据目录、接口地址和凭据通过配置与环境变量传入。例如 `GV_S3_DEVICE` 决定使用 CPU 或 GPU，`GV_S3_DATA_DIR` 决定任务数据位置，`GV_S3_API_URL` 告诉页面到哪里请求后端。真实密钥放在被 Git 忽略的本地配置中，再在启动时注入，代码中只保留无真实值的示例。

程序、虚拟环境、Docker 数据、权重、缓存和交付材料尽量放在 D 盘。安装器下载到 D 盘，不代表 Docker 的镜像与虚拟磁盘也已经在 D 盘，因此还要核对实际数据位置。

## 五、Docker：让程序在另一个环境中运行

### 1. 镜像、容器与 Dockerfile

**通俗解释：镜像像准备好的运行模板，容器是照着模板启动的实例，Dockerfile 是制作模板的步骤。**

镜像包含程序及所需依赖，容器在其基础上运行。它们有助于复现环境，但不会自动把主机显卡驱动、外部账号和业务数据都准备好。容器通常共享所在 Linux 环境的内核，也不能简单理解为一整台独立虚拟机。

项目 `Dockerfile` 使用 Python 3.12 的 Linux 基础镜像，安装系统库、PyTorch 和项目依赖，复制程序文件，最后使用非 root 用户启动 API。默认构建为 CPU 版本，GPU 构建选择相应的 PyTorch 软件源。

`.dockerignore` 负责排除不应进入构建上下文的文件，例如私有配置、虚拟环境和无关大文件。权重通过外部挂载提供，真实密钥不写入 Dockerfile 或镜像层。

### 2. Compose、服务网络与端口

**通俗解释：Compose 像一份开机清单，把需要一起运行的几个服务及它们的连接关系写清楚。**

项目 `compose.yaml` 管理 `api`、`web` 和 `nginx` 三个服务。API 执行任务，Web 提供页面，nginx 统一转发入口。API 与 Web 使用同一应用镜像，通过不同启动命令承担不同职责。

容器之间可以通过服务名连接，例如页面访问 `http://api:8000`。这里的 `api` 是 Compose 网络中的服务名，不是网页访问者电脑上的主机名。对外只映射必要的 nginx 入口，内部数据库和 API 无需单独开放到公网。

`docker compose up -d --wait` 用于在后台启动并等待检查，`docker compose ps` 查看状态，`docker compose stop` 停止服务。停止、重新启动和重新构建镜像是不同操作；普通查看或重启不需要重新下载所有依赖。

### 3. 数据挂载与备份恢复

**通俗解释：挂载让容器使用外面的文件夹，容器换了，重要数据仍留在这个文件夹里。**

本项目把宿主机 `.local/container-data` 挂载到容器 `/data`，其中保存数据库和任务图片；把 `weights` 只读挂载到 `/app/weights`。因此容器可以重建，而历史与模型文件不必跟着丢失。

挂载不是备份。误删除宿主目录仍然会丢数据，所以项目另做了停止写入后的备份、逐文件校验和隔离副本恢复。云端最终四条历史的结果与图片已验证能够恢复；恢复演练没有覆盖唯一的原始成果，也没有重新调用模型。

数据库正在写入时只复制一个文件，未必得到完整一致的快照。本项目的维护流程先检查没有活动任务、停止 API，再复制和核对数据。备份中的运行配置可能含凭据，因此私有恢复归档与公开交付源码包必须分开保存。

### 4. CPU、GPU、CUDA 与容器显卡支持

**通俗解释：GPU 能加速模型运算，但程序、依赖、驱动和容器需要接好，才真正用得上。**

CPU 可以执行模型，但本机 Linux CPU 验证的两张开发图总耗时约为 145 秒和 120 秒，其中第一张包含初次加载。为了演示更流畅，之后进行了本机 GPU 预检和云端 A10 实测。

GPU 方案使用 `compose.gpu.yaml` 请求 GPU，并设置 `cuda:0`；服务器同时需要 NVIDIA 驱动与容器运行支持。`nvidia-smi` 看到显卡只是一个检查步骤，项目还验证了容器内 CUDA 运算和真实模型识别。

云端两张图的本地推理约为 8.895 秒和 8.702 秒，第一张另外有约 4.987 秒初次加载。不同环境的耗时统计边界并不完全一样，所以这些数值是各次实测记录，不作为严格的硬件性能对照实验。

## 六、云服务器：入口、身份和后台任务

### 1. nginx、反向代理、静态资源与 WebSocket

**通俗解释：nginx 像入口处的分流员，把不同请求交给对应服务。**

反向代理是由入口服务接收请求，再转发给内部应用。项目的 `deploy/nginx.conf` 把 `/api/` 请求转给 FastAPI，其余请求转给 Streamlit，因此用户不必分别记住页面端口和 API 端口。

Streamlit 还使用 WebSocket 保持交互连接。它可以理解为一条保持打开的通信连接，所以 nginx 配置了协议升级相关请求头，避免出现页面能打开但交互连接异常的问题。上传大小和等待时间也要与后端配合。

nginx 本身可以直接提供静态文件，例如图片、CSS 和 JavaScript；本项目没有另建独立静态站点，而是通过它转发 Streamlit 页面及页面资源请求。这里要区分“工具能做什么”和“项目实际配置了什么”。

### 2. 身份认证、Bearer 凭据与 JWT

**通俗解释：认证确认来者凭什么访问，授权决定来者允许做什么。**

项目实际采用受控 SSH 通道和 API 共享 Bearer 凭据。Bearer 可以理解为“持有这份凭据即可访问”，页面服务请求 API 时在 `Authorization` 请求头携带它，后端进行校验。配置了凭据时，受保护接口会拒绝无效请求；存活检查是例外。

共享凭据不是每个用户各有账号的登录系统，也不提供用户之间的数据隔离。当前页面主要通过受控通道限定本人和评审访问，不能直接把它描述成具备完整公网多用户登录。

JWT 是另一种常见的令牌格式，通常包含声明并使用签名防止内容被篡改。可以把它理解为“带签名的通行证明”。签名不等于加密，不能认为令牌里的内容天然保密；实际使用还要验证签名、有效期及适用对象等信息。

**本项目没有实现 JWT 登录。** 这部分属于需要理解的学习内容。如果以后改为多人访问，需要补上账号、密码安全存储、令牌签发与验证、过期和退出策略，以及任务的用户归属，不能只把共享凭据改个名字就算实现 JWT。

### 3. 消息队列、生产者、消费者与异步任务

**通俗解释：先发一个排队号码，后台慢慢处理，用户凭号码查询结果。**

异步任务并不表示任务一定同时执行，而是提交者不必一直阻塞等待完整计算。本项目创建接口先保存任务并返回 ID，再由 `ThreadPoolExecutor(max_workers=1)` 在后台顺序执行。网页约每两秒查询状态，任务完成后停止轮询。

创建请求可以理解为任务生产者，后台执行器可以理解为消费者，数据库保存状态和结果。这帮助页面处理耗时推理，也限制模型占用显存。当前只运行一个 API worker，默认最多接受八项尚未完成的任务。

**项目没有部署 Redis、RabbitMQ 或 Celery 等独立队列服务。** Redis 可以承担消息中间存储等职责，Celery 可以管理独立任务消费者；这些是未来扩展路线，不是本次已实现成果。进程内排队加数据库记录，不等于具有可恢复执行上下文的可靠消息队列。

服务重启后，遗留的排队或运行任务会标为 `interrupted`。如果外部请求当时已经开始，则外部侧标为 `unknown`，提示核对结果或账单；不会因为重启自动重新付费。任务状态保存下来，与任务能自动恢复到原来执行位置，是两回事。

### 4. 防重复提交与收费控制

**通俗解释：给同一次提交一个固定编号，重复收到它时查原记录，避免当成新的订单。**

项目要求 `Idempotency-Key`，即幂等键。相同编号、相同图片和选项返回原任务；同一编号配了不同图片或选项则报冲突。它不是“这张图永远只能识别一次”，用户明确创建新任务时仍然可以再次识别。

外部调用最初按批准次数控制，后来按用户要求改为手动模式，取消两次测试上限。但页面默认不勾选，必须明确选择外部方案并创建任务才发送图片；刷新、历史和导出不会收费，失败也不自动重试。

服务商记录中的两次实测总费用为 0.0617103 NEX。这里的外部服务是第三方 NexaVLinks 的兼容接口，模型名称按服务商配置与声明描述，不能说成已经独立核实的 OpenAI 官方直连接口。取消程序次数限制，也不代表后续自动调用获得了无限预算。

## 七、实际遇到的困难，以及它们说明了什么

### 1. 安装完成不等于每个进程都能使用

环境准备时，WSL 已安装，但助手进程查询或访问 Docker 命名管道遇到了权限限制。普通终端中的检查与助手进程的结果不完全相同，因此不能仅凭某次“拒绝访问”判断系统安装失败。

实际处理方式是区分安装问题和执行权限问题：需要管理员操作的组件安装由本人执行，普通终端运行验证脚本，结果保存到 D 盘，再根据结果继续排错。这也说明重装软件并不是所有访问问题的答案。

### 2. 浏览器能联网，镜像构建仍可能失败

Docker 构建先后遇到镜像令牌服务超时、系统软件源访问异常和较大 Python 依赖下载中断。Docker Desktop、Windows 构建客户端和构建步骤的联网位置不同，只在一个界面填代理，不一定覆盖完整下载链路。

项目先验证令牌服务连接，为构建客户端设置当前进程代理，再把合适的构建代理传给安装步骤；系统软件源改用 HTTPS，并保留签名校验。Python 依赖安装拆分为可复用层，使用缓存、合理超时和下载恢复，最后检查依赖一致性。

这个过程让我认识到，排错需要找到失败在哪一层：是获取镜像、安装系统包，还是下载 Python 包。报错都叫“网络失败”，原因与处理方法却不一定相同。

### 3. 引号、路径和目录层级会让正确代码运行失败

本机部署中出现过 PowerShell 向容器传递命令时的引号截断；云端更新又出现权重被复制成多一层目录的问题。后者导致模型无法就绪，但已有历史仍能查看。

修复时分别调整参数引用与目录复制方式，并补查权重位置和 `ready_for_tasks`。最终通过新版网页实际创建 GPU 任务，确认了修复后的识别链路，相关失败记录仍然保留。

这比只看网页是否能打开更可靠。网页、数据库、权重和模型执行各有自己的状态，一个环节正常不能代表全部正常。

### 4. 本机验证、上传校验与云端验收各有作用

为了减少云服务器等待下载的时间，先在本机完成 GPU 预检，准备约 5.15 GB 的镜像、权重和源码包，再上传服务器。传输前后核对 SHA256，可以检查文件是否保持一致，但哈希一致本身不能证明应用一定运行成功。

因此上传后仍检查服务器系统、容器 GPU、真实推理、网页展示和结果导出。两张图片的双侧结果还核对了图片标识，保证比较的是同一张图。它们证明部署链路可用，但只有两张开发图，不能据此给出新的准确率结论。

### 5. 重启、重建、恢复与回滚不能混用

重启是把现有服务停下再启动；重建是重新创建容器；恢复是从备份取回数据；回滚是切换到较早的应用版本。它们解决的问题不同，也都需要明确是否会影响数据。

项目在云端验证了容器重建后四条历史、图片和结果仍然一致，并在隔离副本中验证恢复。新版本→旧版本→新版本的回滚演练在本机独立 Linux 容器项目中完成，不能把它说成云端也重新做了同样演练。

我希望之后能更熟练地判断什么时候只需重启，什么时候需要改配置或重建，以及更新前应该保存哪些数据。

### 6. Git 提交成功，还要知道提交在哪个分支

项目同步时遇到过 Windows 凭据调用问题；解决后，三阶段技术版本同步到了 `stage3` 分支。后来查看仓库默认首页时没有看到新内容，原因是默认 `main` 仍保留二阶段，而三阶段尚未合并。

**通俗解释：提交是一次有编号的快照，分支是一条开发路线，标签给某个版本一个固定名字。** `stage2-submitted` 固定已提交的二阶段版本，`stage3` 继续三阶段工作。推送分支不会自动把它合并到 `main`，源码压缩包也不能代替真实 Git 历史。

当前技术材料版本是 `ff76406`，云端应用版本是 `937529b`；两者的应用运行代码一致，后续提交补充了部署修正、文档和证据。最终合并、标签和交付包仍需要在个人材料确认后一起核对。

### 7. 运行费用也是交付安排的一部分

服务器费用和外部模型调用费用是两套账。服务器按量计费，关闭浏览器、SSH 或 Docker 并不等于释放实例；模型历史回放不产生新的识图费用，但新建外部识别任务可能计费。

项目先准备镜像和权重再开机，并在实际账单中核对学生券抵扣。某一笔抵扣成功只证明那笔已出账费用被抵扣，不能当作最终总费用。完成视频和评审访问安排后，还需要确认是否释放服务器及磁盘，不能因为技术测试完成就忽略资源收尾。

## 八、目前的理解与后续学习方向

我目前适合从完整流程理解项目：页面把图片交给接口，接口创建任务，模型产生结果，数据库保存记录，页面再查询展示；Docker 和 Compose 负责把服务组织起来，nginx 提供入口，SSH 提供受控的远程访问。

但理解这条链路，并不等于已经独立掌握所有实现。我仍需要结合代码熟悉请求参数、数据库事务、Linux 权限、容器网络、异常状态和更新恢复流程。JWT、多用户权限以及独立消息队列目前主要停留在概念和方案理解，没有在这个项目里完成实现。

接下来更实际的学习方向，是先能够沿着任务 ID 找到接口、数据库记录和日志，理解每个报错发生在哪一层，再逐步学习修改一个参数、调整一个接口或完成一次有备份的更新。当前项目仍存在错分、漏检和重复区域，也没有经过高并发或高可用验证；这些边界应如实保留。

完成这一阶段后，我希望自己能够更清楚地说明一个模型应用如何从“可以运行的程序”变成“可以操作、追踪和维护的服务”，并在说明的基础上逐渐提高独立修改与排错的能力。
